# Seatly Sprint 0 — Logical ERD Specification

**Document ID:** SEATLY-ERD-001
**Version:** 1.2
**Date:** 2026-08-10
**Change note:** v1.1 applied `RC-02`–`RC-08` from
[`BASELINE_RECONCILIATION.md`](BASELINE_RECONCILIATION.md), aligning this schema
with `DOMAIN_STATE_MODELS.md`, which is authoritative for states and
transitions. v1.2 carries the resolution of `PD-01`–`PD-10` (`ADR-015`,
`ADR-016`, `ADR-017`): a new `reconciliation_cases` table, cancellation-cutoff
columns on `showtimes` and `bookings`, and a named staff-role split.

### 1. Design stance

- **System of record:** PostgreSQL.
- **Architecture:** Laravel modular monolith; Eloquent for ordinary persistence and SQL/Query Builder for locking and concurrency-critical transitions.
- **Identifiers:** `BIGINT GENERATED BY DEFAULT AS IDENTITY` internal PKs. Externally exposed records also receive an opaque `public_id UUID UNIQUE`.
- **Time:** `timestamptz`, persisted in UTC. Venue timezone controls display and policy boundaries.
- **Money:** `BIGINT` minor units plus `CHAR(3)` ISO currency.
- **States:** `varchar` columns with database `CHECK` constraints rather than PostgreSQL enums, keeping Laravel migrations and later state additions manageable.
- **Deletion:** No soft deletion of transactional records. Catalogue records use `is_active`; referenced halls, seats, and showtimes are retained.
- **Audit/history:** Current authoritative state lives in normal tables; immutable snapshots and append-only event tables preserve historical meaning.

## 2. Entities and constraints

Notation:

- **PK** — primary key
- **FK** — foreign key
- **UQ** — unique constraint
- **CK** — check constraint
- All mutable tables include `created_at`, `updated_at` unless otherwise stated.

### 2.1 Identity and authorization

#### `users`

Use Laravel’s normal authentication table.

Key fields:

- `id BIGINT` **PK**
- `public_id UUID NOT NULL` **UQ**
- `name`, `email`, `password`
- `status VARCHAR` — `ACTIVE`, `DISABLED`, `ANONYMISED`
- `email_verified_at timestamptz NULL`
- `last_active_at timestamptz NULL`

Constraints:

- `UNIQUE (lower(email))` for non-anonymised accounts, implemented as a functional/partial unique index if anonymisation clears or rewrites email.
- **CK:** valid `status`.

#### `roles`

- `id SMALLINT` **PK**
- `code VARCHAR(32)` **UQ** — `CUSTOMER`, `OPERATOR`, `ADMIN`
- `name`

Capabilities are fixed in code against these three codes (`ADR-017`), not stored:

| Role | May do |
|---|---|
| `CUSTOMER` | Own holds, payments, bookings and cancellations |
| `OPERATOR` | Movie, venue, hall and seat maintenance; showtime create, update and publish; all inspection |
| `ADMIN` | Everything `OPERATOR` may do, plus `showtimes.cancel`, `bookings.cancel`, and seat block/unblock |

#### `role_user`

- `user_id` **FK → users**
- `role_id` **FK → roles**
- **PK:** `(user_id, role_id)`

This is sufficient for MVP; do not build a generic permission engine unless authorization requirements expand. The operator/admin split exists because `RELEASE_GATES.md` requires the authorization matrix to be exercised with distinct operator and admin identities — a test that needs something an operator cannot do.

### 2.2 Cinema catalogue and fixed layout

#### `movies`

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `title`
- `synopsis NULL`
- `runtime_minutes SMALLINT`
- `classification NULL`
- `is_active BOOLEAN`

Constraints:

- **CK:** `runtime_minutes > 0`

#### `venues`

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `name`
- `timezone VARCHAR(64)` — baseline `Asia/Kuala_Lumpur`
- address fields as needed
- `is_active BOOLEAN`

Application validation should use an IANA timezone list.

#### `halls`

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `venue_id` **FK → venues**
- `code VARCHAR(32)`
- `name`
- `layout_version INTEGER DEFAULT 1`
- `is_active BOOLEAN`

Constraints:

- **UQ:** `(venue_id, code)`
- **CK:** `layout_version > 0`

Structural changes are prohibited once a published showtime references the hall. Deactivation is preferred over deletion.

#### `seats`

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `hall_id` **FK → halls**
- `row_label VARCHAR(16)`
- `seat_number VARCHAR(16)`
- `display_label VARCHAR(40)`
- `seat_type VARCHAR(16)` — `STANDARD`, `ACCESSIBLE`, `COMPANION`
- `sort_order INTEGER`
- `x_position SMALLINT NULL`
- `y_position SMALLINT NULL`
- `is_active BOOLEAN`

Constraints:

- **UQ:** `(hall_id, row_label, seat_number)`
- **UQ:** `(hall_id, sort_order)`
- **CK:** valid `seat_type`
- **CK:** `sort_order >= 0`

`sort_order` is the canonical locking and display order within a hall; the transactional lock order still uses immutable `seat_id`.

#### `seat_companion_links`

- `accessible_seat_id` **PK, FK → seats**
- `companion_seat_id` **FK → seats, UQ**
- `created_at`

Constraints:

- **CK:** `accessible_seat_id <> companion_seat_id`
- A **deferred constraint trigger** shall enforce:
  - both seats belong to the same hall;
  - accessible side has type `ACCESSIBLE`;
  - companion side has type `COMPANION`;
  - both are active;
  - the declared layout relationship is valid/adjacent according to the hall layout.

The two unique keys ensure a seat cannot participate in multiple pairs. PostgreSQL `CHECK` constraints alone cannot inspect referenced seat rows, so this invariant requires a constraint trigger plus service-level validation.

### 2.3 Showtimes and materialized inventory

#### `showtimes`

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `movie_id` **FK → movies**
- `hall_id` **FK → halls**
- `status VARCHAR(16)` — `DRAFT`, `PUBLISHED`, `CANCELLED`
- `starts_at timestamptz`
- `ends_at timestamptz`
- `sales_open_at timestamptz NULL`
- `sales_close_at timestamptz NULL`
- `price_minor BIGINT`
- `currency CHAR(3)` default `MYR`
- `cancellation_cutoff_minutes INTEGER NOT NULL DEFAULT 120`
- `published_at timestamptz NULL`
- `cancelled_at timestamptz NULL`
- `cancellation_reason_code VARCHAR(64) NULL`
- `version INTEGER DEFAULT 1`

Constraints:

- **CK:** `ends_at > starts_at`
- **CK:** `price_minor >= 0`
- **CK:** currency is uppercase ISO-format: `currency ~ '^[A-Z]{3}$'`
- **CK:** `cancellation_cutoff_minutes >= 0`
- **CK:** `version > 0`
- State-dependent **CK**:
  - `DRAFT`: `published_at IS NULL AND cancelled_at IS NULL`
  - `PUBLISHED`: `published_at IS NOT NULL AND cancelled_at IS NULL`
  - `CANCELLED`: `cancelled_at IS NOT NULL`
- **Exclusion constraint**, requiring `btree_gist`, to prevent overlapping published showtimes in the same hall:

```sql
EXCLUDE USING gist (
    hall_id WITH =,
    tstzrange(starts_at, ends_at, '[)') WITH &&
)
WHERE (status = 'PUBLISHED');
```

Publishing creates all `showtime_seats` in the same transaction. Once published, the movie, hall, schedule, price, and currency should not be edited in place; cancel and recreate when a material correction is required.

**No `ENDED` state (`RC-03`).** A past showtime is not bookable because "on sale"
is derived, not stored:

```sql
status = 'PUBLISHED' AND transaction_timestamp() < starts_at
```

Adding a stored `ENDED` status would put a lifecycle job on the correctness path —
if it failed to run, a finished showtime would still read as bookable. Derivation
keeps the authority in the same transaction as the write.

#### `showtime_seats`

Authoritative mutable seat inventory.

- `showtime_id` **FK → showtimes**
- `seat_id` **FK → seats**
- `status VARCHAR(16)` — `AVAILABLE`, `HELD`, `CONFIRMED`, `BLOCKED`
- `hold_id BIGINT NULL`
- `booking_id BIGINT NULL`
- `hold_expires_at timestamptz NULL`
- `price_minor BIGINT`
- `currency CHAR(3)`
- `version INTEGER DEFAULT 1`
- `blocked_reason_code VARCHAR(64) NULL`
- `updated_at timestamptz`

Constraints:

- **PK:** `(showtime_id, seat_id)`
- **CK:** `price_minor >= 0`
- **CK:** `version > 0`
- State-dependent **CK**:

```text
AVAILABLE:
  hold_id IS NULL
  booking_id IS NULL
  hold_expires_at IS NULL
  blocked_reason_code IS NULL

HELD:
  hold_id IS NOT NULL
  booking_id IS NULL
  hold_expires_at IS NOT NULL
  blocked_reason_code IS NULL

CONFIRMED:
  hold_id IS NULL
  booking_id IS NOT NULL
  hold_expires_at IS NULL
  blocked_reason_code IS NULL

BLOCKED:
  hold_id IS NULL
  booking_id IS NULL
  hold_expires_at IS NULL
  blocked_reason_code IS NOT NULL
```

**Ownership linkage is current, not historical (`RC-02`).** Confirmation
(`INV-03`) clears `hold_id` when it sets `booking_id`; a `CONFIRMED` row therefore
has exactly one current owner and no stale hold pointer. Showtime cancellation of
a confirmed seat (`INV-11`) clears `booking_id` and sets
`blocked_reason_code = 'SHOWTIME_CANCELLED'`, while the booking itself moves to
`SHOWTIME_CANCELLED`.

Which hold produced which booking, and which seats a cancelled booking held, is
recoverable from `hold_items`, `booking_items`, `bookings.hold_id`, and
`audit_events`. This table stores who owns the seat **now**.

Composite ownership FKs, added after owner tables exist:

- `(hold_id, showtime_id)` **FK → holds(id, showtime_id)**
- `(booking_id, showtime_id)` **FK → bookings(id, showtime_id)**

These prevent accidentally linking an inventory row to a hold or booking for another showtime.

`price_minor` and `currency` are copied from the showtime when inventory is materialized. They are the source for hold snapshots, not a dynamically recomputed value.

### 2.4 Holds and checkout snapshots

#### `holds`

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `user_id` **FK → users**
- `showtime_id` **FK → showtimes**
- `status VARCHAR(16)` — `ACTIVE`, `EXPIRED`, `RELEASED`, `CONFIRMED`
- `seat_count SMALLINT`
- `total_minor BIGINT`
- `currency CHAR(3)`
- `created_at timestamptz DEFAULT CURRENT_TIMESTAMP`
- `expires_at timestamptz`
- `closed_at timestamptz NULL`
- `accessible_acknowledged BOOLEAN DEFAULT FALSE`
- `accessible_acknowledged_at timestamptz NULL`
- `accessibility_policy_version VARCHAR(32) NULL`

Constraints:

- **UQ:** `(id, showtime_id)` to support composite inventory FK.
- **UQ:** `(id, user_id, showtime_id)` to support booking consistency FK.
- **CK:** `seat_count BETWEEN 1 AND 8`
- **CK:** `total_minor >= 0`
- **CK:** `expires_at = created_at + interval '5 minutes'`
- **CK:** `expires_at > created_at`
- **CK:** `ACTIVE` implies `closed_at IS NULL`; terminal states imply `closed_at IS NOT NULL`.
- Accessibility acknowledgement fields are either all absent/false or all present/true.

The insert must use PostgreSQL time for both timestamps. Holds are not extended.

#### `hold_items`

Immutable checkout line snapshots.

- `hold_id`
- `showtime_id`
- `seat_id`
- `seat_label_snapshot`
- `row_label_snapshot`
- `seat_number_snapshot`
- `seat_type_snapshot`
- `price_minor`
- `currency`

Constraints:

- **PK:** `(hold_id, seat_id)`
- `(hold_id, showtime_id)` **FK → holds(id, showtime_id)**
- `(showtime_id, seat_id)` **FK → showtime_seats**
- **CK:** `price_minor >= 0`
- **CK:** valid snapshot seat type

A deferred constraint trigger shall verify after hold construction:

- item count equals `holds.seat_count`;
- sum of item amounts equals `holds.total_minor`;
- all item currencies equal hold currency;
- maximum eight distinct seats;
- every selected companion seat’s linked accessible seat is present;
- accessible-seat selection has the required acknowledgement;
- all items belong to the same showtime.

### 2.5 Payment attempts and callback inbox

#### `payments`

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `hold_id` **FK → holds**
- `attempt_number SMALLINT`
- `provider VARCHAR(32)` default `SIMULATED`
- `provider_payment_id VARCHAR(128)`
- `status VARCHAR(32)` — `CREATED`, `PENDING`, `SUCCEEDED`, `FAILED`, `TIMED_OUT`, `RECONCILIATION_REQUIRED`, `LATE_SUCCESS_REFUND_REQUIRED`, `UNRESOLVED`
- `amount_minor BIGINT`
- `currency CHAR(3)`
- `requested_at timestamptz NULL`
- `last_callback_at timestamptz NULL`
- `succeeded_at timestamptz NULL`
- `failed_at timestamptz NULL`
- `reconciliation_reason_code VARCHAR(64) NULL`

Constraints:

- **UQ:** `(hold_id, attempt_number)`
- **UQ:** `(provider, provider_payment_id)`
- **UQ:** `(id, hold_id)` for booking’s composite FK.
- **CK:** `attempt_number BETWEEN 1 AND 3`
- **CK:** `amount_minor >= 0`
- State-dependent timestamp/reconciliation checks.

Do not add real card, account, or bank fields.

The eight statuses match `DOMAIN_STATE_MODELS.md` §7.2 exactly (`RC-04`), and
all of them are now reachable under `ADR-015`. `REFUND_REQUIRED` is a
classification; no refund is executed.

**Up to three attempts per hold (`ADR-015`).** An explicit payment failure leaves
the hold `ACTIVE`, so the customer may retry until `expires_at`; the third
failure releases the hold. `attempt_number` and its unique constraint carry that
sequence. `PAY-01` rejects a fourth with `PAYMENT_ATTEMPT_LIMIT_REACHED`, and
rejects any attempt started within 60 seconds of `expires_at` with
`HOLD_TOO_CLOSE_TO_EXPIRY`.

**No `timeout_at` column (`RC-08`, confirmed by `ADR-015`).** `PAY-05` guards on
a deadline, and that deadline *is* `holds.expires_at`. Storing it twice would
create a second authority for the same instant. If a future decision gives
payment an independent timer, add `timeout_at timestamptz` then and make the
guard read it.

#### `payment_callback_events`

Append-only callback inbox and deduplication record.

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `provider VARCHAR(32)`
- `provider_event_id VARCHAR(128)`
- `provider_payment_id VARCHAR(128) NULL`
- `payment_id BIGINT NULL` **FK → payments**
- `claimed_outcome VARCHAR(32) NULL`
- `claimed_amount_minor BIGINT NULL`
- `claimed_currency CHAR(3) NULL`
- `signature_valid BOOLEAN`
- `payload_hash CHAR(64)`
- `disposition VARCHAR(40)` — the canonical vocabulary below
- `rejection_reason_code VARCHAR(64) NULL`

Dispositions are the sixteen values of `DOMAIN_STATE_MODELS.md` §7.3 plus
`RECEIVED`, the value written when the inbox row is inserted before the domain
transaction runs (`RC-07`):

```text
RECEIVED                        -- inserted, not yet classified
ACCEPTED_SUCCESS
ACCEPTED_FAILURE
DUPLICATE_SAME_PAYLOAD
DUPLICATE_PAYLOAD_MISMATCH
INVALID_SIGNATURE
MALFORMED
UNCORRELATED
AMOUNT_MISMATCH
CURRENCY_MISMATCH
CONTRADICTS_COMMITTED_SUCCESS
CONTRADICTS_COMMITTED_FAILURE
LATE_SUCCESS_NO_CONFIRMATION
LATE_FAILURE_RECORDED
NON_FINAL_ACKNOWLEDGEMENT
IGNORED_ALREADY_TERMINAL
```

Only `RECEIVED` may lack `processed_at`. Every other value is terminal for that
event row.
- `received_at timestamptz`
- `processed_at timestamptz NULL`
- `correlation_id UUID`

Constraints:

- **UQ:** `(provider, provider_event_id)`
- **CK:** claimed amount is null or non-negative.
- **CK:** processed dispositions require `processed_at`.
- Raw callback bodies and secrets are not retained. Store only parsed/redacted values and a cryptographic payload hash.

An unknown or uncorrelated event remains recordable with `payment_id NULL`; it must not mutate inventory.

Payment timeout and contradictory-outcome precedence remain gated policy decisions. The schema supports explicit states without deciding those policies implicitly.

### 2.6 Bookings, tickets, and cancellation

#### `bookings`

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `reference VARCHAR(24)` **UQ**
- `user_id` **FK → users**
- `showtime_id` **FK → showtimes**
- `hold_id` **FK → holds, UQ**
- `payment_id` **FK → payments, UQ**
- `status VARCHAR(24)` — `CONFIRMED`, `CUSTOMER_CANCELLED`, `ADMIN_CANCELLED`, `SHOWTIME_CANCELLED`
- `seat_count SMALLINT`
- `total_minor BIGINT`
- `currency CHAR(3)`
- `confirmed_at timestamptz`
- `cancelled_at timestamptz NULL`
- `movie_title_snapshot`
- `venue_name_snapshot`
- `venue_timezone_snapshot`
- `hall_name_snapshot`
- `showtime_starts_at_snapshot timestamptz`
- `cancellation_cutoff_minutes_snapshot INTEGER NOT NULL`
- `qr_token_hash CHAR(64)`
- `qr_expires_at timestamptz`
- `qr_revoked_at timestamptz NULL`

Constraints:

- **UQ:** `(id, showtime_id)`
- `(hold_id, user_id, showtime_id)` **FK → holds(id, user_id, showtime_id)**
- `(payment_id, hold_id)` **FK → payments(id, hold_id)**
- **CK:** `seat_count BETWEEN 1 AND 8`
- **CK:** `total_minor >= 0`
- **CK:** confirmed status has no cancellation timestamp; cancelled status has one.
- QR stores only a salted/keyed hash, never the presented token.
- QR expiry is showtime end plus four hours; revoke on cancellation.

The unique `hold_id` and `payment_id` enforce at most one booking effect for each intent and successful payment attempt.

`ADMIN_CANCELLED` (`RC-05`) is the target state for `BKG-03`, which `ADR-017`
grants to `ADMIN` only.

`cancellation_cutoff_minutes_snapshot` is copied from
`showtimes.cancellation_cutoff_minutes` at confirmation and is immutable
(`ADR-016`). Cancellation eligibility reads the snapshot, never the live
showtime value, so changing the policy cannot retroactively re-term a booking
that has already been sold — the same reasoning as the price snapshot.

#### `booking_items`

Immutable booked-seat snapshots.

- `booking_id`
- `showtime_id`
- `seat_id`
- `seat_label_snapshot`
- `row_label_snapshot`
- `seat_number_snapshot`
- `seat_type_snapshot`
- `price_minor`
- `currency`

Constraints:

- **PK:** `(booking_id, seat_id)`
- `(booking_id, showtime_id)` **FK → bookings(id, showtime_id)**
- `(showtime_id, seat_id)` **FK → showtime_seats**
- **CK:** non-negative price and valid seat type.

A deferred confirmation trigger shall ensure booking items exactly equal the originating `hold_items`, including amount, currency, seat labels, and seat types. Booking snapshots are immutable.

#### `cancellations`

Records every cancellation command and its decision, for all three cancellation
types. One table replaces the earlier booking-only `booking_cancellations`
(`RC-06`), because the idempotent-decision machinery of
`DOMAIN_STATE_MODELS.md` §9 (`CAN-01`–`CAN-05`) is identical whichever aggregate
is targeted, and showtime cancellation needs a record too (§10.2 step 11).

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `type VARCHAR(24)` — `CUSTOMER_BOOKING`, `ADMIN_BOOKING`, `SHOWTIME`
- `booking_id BIGINT NULL` **FK → bookings**
- `showtime_id BIGINT NULL` **FK → showtimes**
- `requested_by_user_id BIGINT NULL` **FK → users, ON DELETE SET NULL**
- `state VARCHAR(16)` — `REQUESTED`, `APPLIED`, `REJECTED`
- `reason_code VARCHAR(64)` — controlled cause, or rejection reason when rejected
- `request_fingerprint CHAR(64)`
- `requested_at timestamptz`
- `decided_at timestamptz NULL`
- `correlation_id UUID`

Constraints:

- **CK:** the target matches the type —

```text
CUSTOMER_BOOKING, ADMIN_BOOKING:  booking_id  IS NOT NULL AND showtime_id IS NULL
SHOWTIME:                         showtime_id IS NOT NULL AND booking_id  IS NULL
```

- **CK:** `CUSTOMER_BOOKING` requires `requested_by_user_id IS NOT NULL`.
- **CK:** `REQUESTED` implies `decided_at IS NULL`; `APPLIED` and `REJECTED`
  imply `decided_at IS NOT NULL`.
- Partial **UQ:** at most one applied cancellation per target —

```sql
UNIQUE (booking_id)  WHERE state = 'APPLIED' AND booking_id  IS NOT NULL;
UNIQUE (showtime_id) WHERE state = 'APPLIED' AND showtime_id IS NOT NULL;
```

- The command's scoped idempotency key lives in `idempotency_keys`; this table
  records the decision it produced.
- No individual booked-seat cancellation in MVP.

Rejection reasons use the `DOMAIN_STATE_MODELS.md` §9.1 list —
`NOT_OWNER`, `UNAUTHORIZED`, `NOT_FOUND_OR_NOT_DISCLOSED`, `ALREADY_CANCELLED`,
`SHOWTIME_NOT_ON_SALE`, `CUTOFF_REACHED`, `BOOKING_NOT_CONFIRMED`,
`INVALID_REASON`, `POLICY_NOT_ENABLED`. The earlier `outcome` values
`ALREADY_CANCELLED` and `INELIGIBLE` were reasons, not states, and now appear
here under `state = 'REJECTED'`.

A rejected authorization may return a generic external response while this row
records the precise protected reason.

#### `reconciliation_cases`

Operational visibility for ambiguous, contradictory, late, or paid-but-unbooked
outcomes. This is the third record type `DOMAIN_STATE_MODELS.md` §7.1 has always
required and the schema never grew (`ADR-015`).

- `id BIGINT` **PK**
- `public_id UUID` **UQ**
- `payment_id BIGINT NULL` **FK → payments**
- `booking_id BIGINT NULL` **FK → bookings**
- `state VARCHAR(16)` — `OPEN`, `RESOLVED`, `UNRESOLVED`
- `reason_code VARCHAR(64)`
- `opened_at timestamptz`
- `closed_at timestamptz NULL`
- `correlation_id UUID`

Constraints:

- **CK:** at least one target — `payment_id IS NOT NULL OR booking_id IS NOT NULL`.
- **CK:** `OPEN` implies `closed_at IS NULL`; the other states imply it is set.
- Partial **UQ:** one open case per payment attempt —

```sql
UNIQUE (payment_id) WHERE state = 'OPEN' AND payment_id IS NOT NULL;
```

Reason codes include `PAYMENT_TIMED_OUT`, `LATE_SUCCESS_REFUND_DUE`,
`CONTRADICTORY_OUTCOME`, `SHOWTIME_CANCELLED_REFUND_DUE`.

**Why this is not a status column on `payments`.** Most cases could live there,
but two cannot, because in both the payment is `SUCCEEDED` and §7.6 forbids it
from moving:

- `PAY-13` — a committed success later contradicted by a failure callback. The
  booking stands; the contradiction still has to be visible somewhere.
- `ADR-017` showtime cancellation — every confirmed booking is owed a refund, and
  its payment succeeded entirely legitimately.

A case is opened by `PAY-05`, `PAY-06`, `PAY-08`, `PAY-09`, `PAY-11b`, `PAY-13`,
and by showtime cancellation. `PAY-05b` deliberately opens none: initiation was
never durably sent, so nothing is ambiguous. Nothing in MVP resolves a case by
hand — operator scope is inspection only — so `RESOLVED` is reached by a later
callback and `UNRESOLVED` by the 24-hour closure job.

### 2.7 Reliability and traceability

#### `idempotency_keys`

- `id BIGINT` **PK**
- `scope VARCHAR(64)`
- `principal_key VARCHAR(128)` — non-PII namespace such as `user:123`
- `key_hash CHAR(64)`
- `request_fingerprint CHAR(64)`
- `status VARCHAR(16)` — `IN_PROGRESS`, `COMPLETED`, `FAILED`
- `http_status SMALLINT NULL`
- `result_type VARCHAR(64) NULL`
- `result_id BIGINT NULL`
- `response_snapshot JSONB NULL` — minimal/redacted
- `created_at`, `completed_at NULL`, `expires_at`

Constraints:

- **UQ:** `(scope, principal_key, key_hash)`
- **CK:** completed records have completion/result response data.
- Store hashes, not raw client keys.
- Retention: 30 days.

`result_type/result_id` is intentionally a logical polymorphic reference; enforce allowed result types in application code.

#### `outbox_events`

- `id UUID` **PK**
- `aggregate_type VARCHAR(64)`
- `aggregate_id BIGINT`
- `event_type VARCHAR(128)`
- `payload JSONB`
- `correlation_id UUID`
- `occurred_at timestamptz`
- `available_at timestamptz`
- `processed_at timestamptz NULL`
- `attempt_count INTEGER DEFAULT 0`
- `last_error_code VARCHAR(64) NULL`

Constraints:

- **CK:** `attempt_count >= 0`
- Payloads must be versioned and contain no unnecessary PII, callback secrets, or raw QR values.
- Insert in the same transaction as the corresponding domain mutation.

Laravel’s standard `jobs`, `failed_jobs`, and job batch tables remain infrastructure tables and are not part of the logical domain ERD.

#### `audit_events`

Append-only business/security audit trail.

- `id BIGINT` **PK**
- `event_id UUID` **UQ**
- `occurred_at timestamptz`
- `actor_type VARCHAR(16)` — `USER`, `SYSTEM`, `PROVIDER`
- `actor_user_id BIGINT NULL` **FK → users, ON DELETE SET NULL**
- `action VARCHAR(128)`
- `subject_type VARCHAR(64)`
- `subject_id BIGINT NULL`
- `correlation_id UUID`
- `result VARCHAR(32)`
- `reason_code VARCHAR(64) NULL`
- `metadata JSONB` — redacted/minimised

The application DB role should have `INSERT` and `SELECT` but no `UPDATE` or `DELETE` on this table. Retention is 180 days.

## 3. Core cardinalities

```text
Venue       1 ──< Hall
Hall        1 ──< Seat
Seat        0..1 ── 0..1 SeatCompanionLink, in a directed accessible→companion pair

Movie       1 ──< Showtime
Hall        1 ──< Showtime
Showtime    1 ──< ShowtimeSeat
Seat        1 ──< ShowtimeSeat

User        1 ──< Hold
Showtime    1 ──< Hold
Hold        1 ──< HoldItem
ShowtimeSeat 1 ──< HoldItem over history

Hold        1 ──< Payment
Payment     1 ──< PaymentCallbackEvent
Hold        0..1 ── 1 Booking
Payment     0..1 ── 1 Booking
Booking     1 ──< BookingItem
Booking     1 ──< Cancellation attempts, type CUSTOMER_BOOKING or ADMIN_BOOKING
Showtime    1 ──< Cancellation attempts, type SHOWTIME
Payment     1 ──< ReconciliationCase, at most one OPEN at a time
Booking     1 ──< ReconciliationCase
ShowtimeSeat 1 ──< BookingItem over history
```

At any instant, each `showtime_seat` has zero or one current hold owner and zero or one current booking owner. Historical owners are preserved in item tables and audit events.

## 5. Snapshot and history strategy

1. **Current inventory**
   - `showtime_seats` is the only current seat-allocation authority.
   - Expired `HELD` rows are treated as reclaimable during write-path validation even before the cleanup worker changes their stored status.

2. **Checkout snapshot**
   - `holds` captures total, currency, acknowledgement, and deadline.
   - `hold_items` captures exact seat labels/types and line prices.
   - Neither is edited after creation except hold lifecycle fields.

3. **Confirmed history**
   - `bookings` captures movie, venue, hall, timezone, and scheduled-start display facts.
   - `booking_items` captures seat labels/types and prices.
   - Later catalogue edits or seat deactivation cannot alter booking history.

4. **Operational history**
   - `payment_callback_events` is the deduplicated callback inbox.
   - `cancellations` records cancellation decisions for bookings and showtimes.
   - `reconciliation_cases` records money that needs a human answer.
   - `audit_events` records append-only actor/transition/result history.
   - `outbox_events` records durable integration events, not a general audit log.

5. **Mutability**
   - Snapshot/item rows are immutable through normal application roles.
   - Do not use Eloquent observers to create snapshots or outbox records; explicit application actions write them within the authoritative transaction.

## 6. Global lock order

Every transaction touching inventory shall acquire locks in this order:

1. Existing `idempotency_keys` or newly inserted callback inbox row for the logical command.
2. `showtimes` row.
3. Requested `showtime_seats`, ordered by `seat_id ASC`.
4. `holds`, ordered by `id ASC`.
5. `payments`, ordered by `id ASC`.
6. `bookings`, ordered by `id ASC`.
7. Insert/update child records.
8. Insert `outbox_events` and `audit_events` last.

Practical rules:

- Read IDs needed to construct the lock set before the transaction or through non-locking reads, but revalidate everything after locks are acquired.
- Never lock seats in browser/request order.
- Never acquire a showtime lock after holding a seat, hold, payment, or booking lock.
- Cancellation, confirmation, expiry, blocking, and showtime cancellation must use the same order.
- For multiple showtimes, process `showtime_id ASC`, then `seat_id ASC`.
- The expiry worker should discover candidate hold IDs without locking them, then process each using the global order. Do not begin by locking arbitrary hold rows.
- Worker batching may use queue rows with `SKIP LOCKED`; it must not use `SKIP LOCKED` to bypass authoritative seat validation.

### Atomic hold transaction

```text
Insert/lock idempotency record
→ lock showtime
→ reject non-published/non-sale showtime
→ lock all requested showtime_seats by seat_id
→ inline-expire/reclaim eligible stale HELD rows
→ validate availability, count, accessible declaration, and companion pair
→ insert hold and hold_items
→ mark all rows HELD with common hold_id/deadline
→ insert outbox and audit
→ commit
```

### Confirmation transaction

```text
Deduplicate callback event
→ identify hold and seat set
→ lock showtime
→ lock exact showtime_seats by seat_id
→ lock hold
→ lock payment
→ revalidate callback, amount/currency, hold deadline, pair coverage,
  showtime state, and current seat ownership
→ insert booking and booking_items
→ mark all inventory rows CONFIRMED
→ mark hold CONFIRMED and payment SUCCEEDED
→ disposition callback
→ insert outbox and audit
→ commit
```

A late success records `RECONCILIATION_REQUIRED`/`LATE_SUCCESS`; it must never re-hold or reclaim seats.

1. Enable required extensions:
   - `pgcrypto` for UUID generation if used.

2. Create users/authentication tables.
